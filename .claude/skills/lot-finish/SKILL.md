# Terminer un lot

Issues du lot : $ARGUMENTS (sinon celles prises en charge sur la branche courante).
Références : `.harness/docs/CONVENTIONS.md` (PR, commentaires), `.harness/docs/ORCHESTRATION.md` §3 (revue
adversariale), `.harness/docs/CI-BUDGET.md` (sinon les mêmes fichiers sous `${CLAUDE_PLUGIN_ROOT}/docs/`).

1. **Contrôles locaux** : tests, lint, couverture, script de CI locale du projet (`CLAUDE.md` › Build et tests).
   `git status` : aucun fichier suivi oublié, aucun artefact. Chaque nouveau test a été vu **en échec** sans le
   changement. Code d'app non compilable ici (cloud Linux) : relu avec une rigueur de compilateur, et noté.
2. **Auto-relecture** : skill `/lessons-check` (ou à la main contre `LESSONS.md`). Docs, plan, réglementation à jour
   dans les mêmes commits. Version et Nouveautés **non** touchées (gérées à l'intégration).
3. **Revue adversariale** : un sous-agent neuf, **d'un autre modèle** que l'auteur, en lecture seule, reçoit seulement
   le diff (`git diff origin/<intégration>...HEAD`), la spec, `ESSENTIEL.md`, `LESSONS.md`, avec la consigne
   d'ORCHESTRATION.md §3 — jamais tes conclusions. Corriger chaque constat Haute/Moyenne en un commit, faire revérifier.
4. **Commits** : atomiques par issue, en français, style `git log`, attribution de la session en fin de message.
5. **Un seul push**, puis PR **en brouillon** vers la branche d'intégration. Corps : `Closes #n` une ligne par issue ;
   résumé par issue ; vérification ; points de vigilance / non testé ; `## Changelog` (côté utilisateur, ou
   « Aucun ») ; modèles auteur / relecteur ; ligne de génération. Titre dans le style des PR précédentes.
6. **Commentaires de fin** sur chaque issue : fait, lien de la PR, ce qui reste, décisions prises (option la plus simple
   retenue si ambiguïté), à valider sur l'appareil ; pied `---` / `_Generated by [Claude Code](https://claude.ai/code)_`.
   Mettre à jour la colonne PR du tableau de l'issue parapluie ; la fermer si tous ses points le sont.
7. **Travail découvert** : une issue labellisée par sujet (jamais seulement une note).
8. Ne pas passer « Ready for review » ni merger sans l'accord de l'opérateur, sauf politique contraire du projet.
   Rendre compte : lien de la PR, ce qui reste, ce qu'il faut vérifier sur Mac (`/review-round` pour la suite).
