# 0014 — BBCode preview renderer: HFR's own rendering model in `HFRParsing`, output through the LOT-034 normalizer

**Status:** Proposed — 2026-11-02 (session `cloud/lot-097`, first deliverable of [LOT-097](../lots/LOT-097-bbcode-preview-renderer.md), [#189](https://github.com/ezzz/HFRnow/issues/189); accepted when merged by the orchestrator or the maintainer; the operator's choice O-1 below is recorded on the issue)

## Context

FEAT-013 ([#157](https://github.com/ezzz/HFRnow/issues/157), proposed by Bybifok) asks for a preview of a message "exactly as HFR will render it" before it is sent. The legacy app has no preview (the lot's legacy sources are empty; the only BBCode code in the legacy Swift layer is the insertion engine, `HFRswift/Swift/ReplyComposer.swift:99-205` at `2440d79`, which wraps a selection in tags and never renders). The reader shows posted messages through the chain of [ADR 0006](0006-content-normalization-in-parsing.md): HFR's HTML → `MessageContentNormalizer` (LOT-034, the sanitizer of record) → `MessageContent` → the app's `TopicHTMLBuilder` and `ReaderWebController` (LOT-083: `hfrreader:` scheme, CSP `script-src 'none'`, content JavaScript off, images through the cookie-less client and policy C).

What HFR does with BBCode is known from two kinds of captured pairs, a source and its rendering by HFR:

- **Run 9** ([#400](https://github.com/ezzz/HFRnow/pull/400), 2026-11-02, [HFR-PROTOCOL §6b "BBCode round trip"](../HFR-PROTOCOL.md#6b-live-observations-from-the-capture-corpus-lot-001-2026-10-26)): `W61` posted one message holding every tag of the composer toolbar help but `email` (`R40a`: `b i u strike spoiler quote url img fixed email cpp` and the bullet `[*]`), the two forms of `url`, a `[color=]` and a `[list]` tag, nested and unclosed tags, raw HTML characters; `R95c` is its edit form (the source comes back HTML-escaped in the `textarea`, CRLF kept); `R95d` is HFR's own preview, `POST /apercu.php` (form `apercu_form` of every composer: `hash_check`, `apercu_contenu`, `apercu_smiley`, `config`). `W62` / `R95h` do the same for BMP emoji.
- **The LOT-001 corpus**: the quote form of a message gives its stored source back in `[quotemsg=…]…[/quotemsg]` (`R41a`, `R41b`, `R42`), and the thread page `R20` shows the same messages rendered. These pairs cover what run 9 did not post: smileys (`:ange:` → `<img …/icones/smilies/ange.gif alt=":ange:" title=":ange:">`, `:d` typed → `alt=":d" title=":D"`, `[:user]` → `/images/perso/user.gif`), the toolbar's colour syntax (`[#0055aa]…[/#0055aa]` → `<span style="color:#0055aa">`; the toolbar inserts `'['+bgColor+']'`, `R40a`, so `W61`'s `[color=…]` tested a syntax HFR does not have), crossed tags (`[u][b]x[/u][/b]` → `<span class="u"><strong>x</span></strong>`: HFR writes crossed HTML and leaves the repair to the browser), blank lines, trailing and leading spaces, and `[url]` without a scheme. The prefill is HFR's re-serialization, HTML-escaped in the `textarea`, not the raw bytes: it writes every `[img]` as `[url]` (`R41a` against `R20`) and drops the citation a message starts with (`R41b`), which a test gives back or sets aside.

HFR itself has several renderings of one source: the message on the thread page and `/apercu.php` agree on the structure (the thread wraps the message in a `<p>` the preview omits: `R20` `para2666649` against the `R41a` review; the #400 MANIFEST says the preview "equals the message body once whitespace is removed, apart from the opening `<p>`", measured on private raw pages that are not published, so what the removed whitespace covers is unknown and the one whitespace row that rests on `/apercu.php` alone, `fixed`, waits on LOT-097 spec Pending 10); the "Vue Rapide" reviews under the composer and the edit form write `[img]` as a link and substitute no smiley (`R95c`, `R41a`).

Questions the issue leaves to this ADR: where the renderer lives (`HFRParsing` or the app), its input and output, how it stays faithful to HFR's rendering, and its security model.

### Options considered

1. **Local renderer in `HFRParsing`, writing HFR's HTML string and producing `MessageContent` through the LOT-034 normalizer.** BBCode text → the HTML string HFR writes for it (only the shapes the pairs prove) → `MessageContentNormalizer.normalize(contentHTML:)` → `MessageContent`. The reader displays it with the code it already has.
2. **Local renderer building a DOM directly** (a parser matching tags on a stack, a writer producing a well-formed SwiftSoup tree handed to the normalizer). Considered first; rejected after the review of this ADR: HFR does not match tags on a stack. It rewrites the text tag by tag and writes crossed HTML (`R41a` → `R20`), which the HTML5 tree builder then repairs; a DOM writer has to re-implement those repairs (`tbody` insertion, crossed-tag adoption, `<p>` auto-closing before blocks, the stray `</p>`) and diverges on every crossed or block-in-inline case. Writing the string and parsing it with the same tree builder as the posted message makes those repairs identical by construction.
3. **Local renderer in the app**, writing HTML strings or an `AttributedString` directly. Rejected: ADR 0002 keeps SwiftSoup out of the app, so the app would be a second producer of message HTML outside the sanitizer of record (ADR 0006), with its own escaping and its own stylesheet to keep in step with the reader; and it would not be tested on Linux against the captures.
4. **Server preview**: `POST /apercu.php` through the account's session, a flow in `HFRClient`. The only rendering that is exact by construction, smileys and future HFR changes included. Not the lot's deliverable (the lot is "BBCode text → `MessageContent`", [LOTS.md](../LOTS.md), and `HFRParsing` is its module), but a real product option: see O-1 below. It stays the **oracle** of the local renderer's tests whatever the operator decides.
5. **A typed BBCode AST as a public type in `HFRModels`**, rendered by the app. Rejected for the same reason as ADR 0006 option 3: a second renderer of message content with its own CSS; and the insertion engine of LOT-085 and the toolbar of LOT-174 work on the text, not on a tree.
6. **Port of a third-party BBCode parser** (ultra-hfr `HFRContent`, MPL-2.0; redface2 `BbcodeContentParser`). Rejected: ideas only, no copy (license and AGENTS.md §3.3); both target their own rendering, not HFR's HTML shapes.

## Decision

Option 1 for the lot. **O-1, the operator's choice** (FEAT-013 says "exact", and no local renderer is exact by construction): (a) the local renderer alone, labelled as a preview; (b) the local renderer plus an on-demand "aperçu HFR" action calling `/apercu.php` (a later `HFRClient` lot: session, `hash_check`, one POST per request, the draft leaves the device when the member asks); (c) `/apercu.php` only, no local renderer. What (a) shows otherwise than HFR today, until the pairs of #443 land: `[email]` as text (a toolbar tag, `R40a`), `[cpp]` without colours; what it may show otherwise (uncaptured): named colours (the toolbar inserts the palette's `bgColor`, `R40a`; which values the palette offers is not captured), bullets on several lines, smiley codes glued to a word or inside a URL, URLs with another scheme or a host and port without a scheme; what (c) would get right by construction, at the price of a request per preview. The ADR recommends (a) now and (b) if users report differences: the local renderer is measured against HFR's own rendering on every captured pair, costs no request, works offline and sends nothing before the member decides to post; (b) adds the exact answer where it is wanted without reversing those properties; (c) gives up the offline and silent preview (composing needs no session until the send; the preview would). LOT-097 proceeds with option 1 under (a) or (b); under (c) it is closed as not planned and a new lot is opened in `HFRClient`.

### 1. Module and shape

- `BBCodeRenderer` is a public, pure function of `HFRParsing`: `render(_ source: String, options: BBCodeRenderOptions = .init(), relativeTo page: URL = HFRURL.base) throws(ParsingError) -> MessageContent`. No I/O, no global state; only a backend failure throws (`malformedDocument`), as `MessageContentNormalizer.normalize(contentHTML:)`. It depends on LOT-034 (the normalizer) and LOT-020 (`HFRURL`); `scripts/check-lot-deps.py` keeps passing (`HFRParsing` → `HFRParsing`). [ARCHITECTURE.md](../ARCHITECTURE.md) names the module's second kind of member: "BBCode → models" for the preview, next to "HTML → models".
- Internally, one `internal` writer, `HFRBBCodeWriter`, follows **HFR's own model**: every text run is escaped by one function (the four characters HFR escapes, `R95d`: `&lt;b&gt;`, `&amp;`, `&#034;`) and the text is rewritten pass by pass, one pass per tag, each pass a single scan of the text with the next closing tag searched once (no regex over the message, no rescans: linear in the source length whatever the nesting, unclosed tags included). Raw blocks (`cpp`, `code`, `fixed`) go first, then the whitespace rule, links and images, smileys (on the text as typed, so a code never matches inside an entity of the escaping), then the escaping of the remaining text, blocks (`quote`, `spoiler`, nested pairs written inside out), colour, inline tags (non-greedy pairs, left to right, so crossed tags come out crossed exactly as HFR writes them), bullets. The fragments a later pass must not touch (URLs, images, smileys, raw blocks) are held in placeholders; `&nbsp;` is written as the entity, as HFR does. The string is then parsed **on the reader's own path, twice as the reader does**: a first parse inside the same markup as the thread page (`td > div#para…`, the clear trailer last, the message's `<p>` left open as HFR leaves it), serialized back as `MessageBlockParser.contentHTML` does, then `MessageContentNormalizer.normalize(contentHTML:)`, which parses that serialization again. The two parses matter for crossed tags: the first serialization of `<span><strong>x</span></strong>` loses a `</strong>` and the second parse reopens the `<strong>` (`R20` `para2666649`: 37 `<strong>` for 36 `</strong>` once serialized from the page, 38 for 38 once normalized), while a single parse, or a string ending with an explicit `</p>`, gives 37 for 37; the test on that pair asserts those counts. The public surface is `render` alone; no recursive value type is built.
- `BBCodeRenderOptions` carries what HFR's own preview form takes: `smileysEnabled` (the composer's `smiley` checkbox, sent as `apercu_smiley`; HFR reads the value: checked disables smileys, HFR-PROTOCOL §6b "Checkbox values") and the **smiley table** (codes → image URLs: `CommonSmileyCatalog` plus the member's personal smileys, built by the app). The table is data passed in, never a dependency of `HFRParsing` on the app or on `HFRStorage`; a URL of the table goes through the normalizer like every other URL (a non-smiley host becomes a policy-C image, not a smiley).

### 2. Input and output contract

- **Input**: the composer's text as the posting flow will send it: line breaks are read as CRLF whatever the source holds (LOT-048 sends CRLF, `PostingBody`), because HFR's whitespace rule reads the CR; the three noncharacters the writer uses as markers (U+FFFF, U+FFFE, U+FDD0) are dropped (no keyboard types them, and HFR's handling of a noncharacter is pending capture); characters above U+FFFF are text, because LOT-048 refuses such a text before any request (`W12`: HFR would truncate). `page` is the topic page the message is posted to, so relative links resolve as the reader will resolve them on the posted message.
- **Output**: a `MessageContent` **indistinguishable from the one the reader will get once the message is posted**: `html` is the normalized body, `signatureHTML` is nil (the signature is HFR's, added at post time, never previewed), `images`, `smileys`, `links` and `embeds` are the typed lists the normalizer derives, so the reader applies the same image policy, smiley bundling and video placeholders to the preview as to a posted message. The context contract of LOT-034 applies unchanged: `html` is body markup for element content only.
- **Fidelity target**: for every captured pair, `render(source)` equals `normalize(HFR's rendered body)` field by field, after the reductions the spec lists and counts (LESSONS 51): the `[cpp]` syntax-colour spans unwrapped from the oracle (the renderer writes a plain code block); for a `/apercu.php` oracle, the template's leading line break removed and the thread's opening `<p>` added (its clear trailer stays and is dropped by the normalizer on both sides); for a quote-prefill source, the `textarea` entities decoded, the `[img]` tags given back and the anonymizer's per-fixture pseudonyms mapped. Nothing else: the `\r` HFR leaves in the text is written by the renderer and compared like any character. Today the pairs are `W61` / `R95d`, `W62` / `R95h`, `R41a` → `R20` (message 2666649, 34 KB: colour, crossed tags, 11 images, 131 links, smileys, blank lines), `R42` → `R20` (2666682), `R41b` → `R20` (2666695).

### 3. Faithful only where proven

- The writer knows **one shape per tag**, copied from a captured pair and cited in the spec's rendering table ([LOT-097 §Behaviour](../lots/LOT-097-bbcode-preview-renderer.md#behaviour)): `b` → `strong`, `i` → `em`, `u` → `span.u`, `strike` → `strike`, `[#RRGGBB]` → `span[style=color:#RRGGBB]`; `spoiler` and `quote` close the paragraph and open `div.container > table.spoiler|quote > tr.none > td` with their header, the spoiler body in `div.Topic.masque > p`, the quote body in `p` ending with a `<br />`; `fixed`, `code` and `cpp` close the paragraph and open `table.fixed|code > tr.none > td`, the code body as `ol.olcode > li` per line; `url` (both forms) → `a.cLink`, its text trimmed of its spaces, `http://` added to a URL with no `scheme:` prefix (another scheme is left to the normalizer, which drops it); `img` → `img` with `alt` and `title` equal to the URL; a smiley code → `img` with `alt` as typed and `title` the catalogue's code, matched whatever its case, anywhere but inside a word starting like a URL (`http://`, `https://`, `www.`; what HFR does there is pending capture); `[*]` → `ul > li` for the rest of its line. Attributes HFR adds and the normalizer drops (`onclick`, `style="cursor:pointer;"`, `id="codeN"`, `onload`, `style="margin: 5px"`, `target`, `rel`, the header's `font-family`) are not emitted: they are outside the ADR 0006 contract, and equality is measured after normalization.
- **One whitespace rule** for plain text, `fixed` and `code`, derived from the pairs: in a run of spaces and CRs, the first character becomes `&nbsp;` when the run starts a line (right after a LF; the start of the message is not a line start; in `code`, every run of two or more, and a run of one at a line start), then the run is read two by two, the first of a pair kept, the second `&nbsp;`; a LF becomes `<br />`.
- **Everything else is text.** A tag outside the table, a closing tag without its opening, an opening tag never closed, `[color=…]`, `[list]`, a second `[*]` on a bullet line: the brackets stay in the text, which is what HFR does on the cases captured (`R95d`). This is also the acceptance criterion "unknown tags are shown as text, never as HTML". A tag HFR knows and the table does not (`[email]`; a named colour if the palette offers one) previews as text where HFR renders it: a listed gap, never a guess.
- **Where one pair allows several rules, the spec picks the narrowest rule that reproduces the pair, names the default it gives every uncaptured case, and the capture that settles it.** The gaps are rows of the spec's "Pending capture" list and of the capture issue this lot opened ([#443](https://github.com/ezzz/HFRnow/issues/443), `host: mac`, readable through `/apercu.php` without posting): `[email]`, named colours, bullets on several lines, `[cpp]` and `[code]` syntax colours (`R27b` colours `#include` and comments in a `table.code` whose tag is unknown), `[quotemsg=…]`, the nesting of one tag in itself and of blocks in inline tags, `url` and `img` with other schemes or targets, bare URLs in text and smiley codes inside them or glued to a word, tabs, odd runs, HFR's limits, and the preview → thread identity for smileys (the reviews substitute none).
- A fidelity gap is a **difference to list, never a guess to fill**: the renderer is extended as pairs land (each new pair becomes a differential test first), and the preview says nothing about how exact it is; LOT-152 labels it per O-1.

### 4. Security model

- **No markup from member text, ever.** Every text run is escaped by one function before the tags are written around it; a tag's URL, a link's text and a smiley's code are escaped on their way into attribute values and element content; the fragments later passes must not rewrite are placeholders built from noncharacters stripped from the source, and a URL holding one is text. Every pass works on **Unicode scalars**, never on `Character`s: Swift's `replacing` and `firstRange` compare grapheme clusters, so a `"` or a `]` followed by a combining mark would escape the escaping and the tag syntax (found by the code review). A mistake there degrades to wrong text or a dropped attribute, never to script: the normalizer parses the string as the sanitizer of record.
- **The sanitizer of record runs on the preview as on every message.** `MessageContentNormalizer`: allow-listed elements, attributes and classes, `on*` and `id` dropped, every `href` and `src` resolved and kept only with an `http(s)` scheme (ADR 0006 amendment 1), so `[url=javascript:…]` previews as text and `[img]data:…[/img]` is removed, whatever HFR would do with them (not captured, and irrelevant to our own display); `[url]G3Ferrari / Optima[/url]`, which HFR links to `http://G3Ferrari / Optima `, previews as text, as the normalizer already shows that posted message (`R20`).
- **The same display stack, nothing weaker.** LOT-152 shows the preview with the reader's `TopicHTMLBuilder` and `ReaderWebController` (`hfrreader:` scheme, CSP `default-src 'none'; script-src 'none'`, content JavaScript off, `reader.js` in its own content world, every image through the cookie-less client and policy C, link taps handed to the app). A preview never gets a second web view, a `loadHTMLString` with a file base URL (the legacy hazard of audit C §5.2) or a relaxed policy. An `[img]` in a draft is therefore fetched with the same rules as an image in a posted message: blocked on private hosts, third-party hosts on tap or per the setting.
- **Local and silent.** Rendering sends nothing anywhere: no request to HFR, no token, no cookie; the draft leaves the device only when the member sends it (or asks for the server preview of O-1 (b), if the operator chooses it). The preview cannot be flood-limited, logged out or rate-limited, and works offline.
- **Bounded work.** Every pass is one scan of the text (the next closing tag or bracket is searched once and remembered; a rejected URL argument is checked on its slice before any copy; nested blocks are matched in one pass and written in a second; the colour closes are indexed once; the whole smiley table is matched in one scan through a trie prepared once per table by `BBCodeRenderOptions` (not per preview), so a position costs at most the longest code whatever the number of codes, the word a smiley sits in bounded once), so the writer is linear in the source length, nested blocks, unclosed tags, rejected arguments and walls of smileys included, for a given table; no recursion, no value type that grows with nesting. Measured: eighteen shapes of 32 to 172 KB (nesting, unclosed tags, unclosed and stray colours, rejected URL arguments, glued smileys, a URL followed by smileys, prose and a `[:perso` wall with the bundled 59-code catalogue plus a thousand personal codes, repeated crossed tags) each cost at most about four times more at four times the size (asserted shape by shape), 2 to 300 ms each at 8 000 repeats on a debug build. **The whole render is not linear on one shape**: repeated crossed tags (`[u][b]x[/u][/b]` on every line) cost the normalizer's parse superlinearly, because each repair reopens the `<strong>` around what follows (measured: 1.3 s at 32 KB, 4.2 s at 64 KB, 14 s at 128 KB on a debug build, the page parse staying linear). The reader pays the same on the posted message (LOT-034 normalizer, SwiftSoup), so the preview is right; LOT-152 therefore renders off the main actor and debounced, and the normalizer's cost has its own issue ([#445](https://github.com/ezzz/HFRnow/issues/445)). The whole render, SwiftSoup's two parses and the normalizer included, takes about 12 s for 10 000 nested tags on a debug build (a robustness check without a wall-clock bound, the suite running in parallel). HFR's own limits are not known and not imitated (pending capture).

### 5. Where the facts live

The rendering table (tag → shape → capture) is in the lot spec; verified facts go to HFR-PROTOCOL §6c under `### LOT-097` once a parser test asserts them (§6b already holds the round-trip facts of run 9). The module rules (ADR 0001, 0002, 0006, 0008) are unchanged except for the one line of ARCHITECTURE.md naming the new kind of member; `HFRClient` is not involved unless O-1 (b) or (c) is chosen.

## Consequences

- The preview and the posted message are rendered by **one** code path after the BBCode stage: the reader's stylesheet, image policy, spoiler toggle and smiley bundling apply to both without duplication, and a LOT-034 fix reaches the preview for free.
- Fidelity is **measured** (differential tests on every captured pair, five today), **bounded** (the spec's rendering table and pending list say exactly what is and is not reproduced) and **extensible** (a new pair → a new test → a new row). The capture issue [#443](https://github.com/ezzz/HFRnow/issues/443) lists what the next Mac session captures.
- `/apercu.php` is documented as HFR's own preview and stays the oracle; O-1 decides whether the app calls it.
- The app side (LOT-152) is thin: build the smiley table (catalogue plus personal smileys) once into `BBCodeRenderOptions`, read the `smiley` checkbox, call `render` off the main actor and debounced (the render is not linear on repeated crossed tags, §4), build a `ReaderPage` with one message, show it in the reader stack, label it per O-1.
- Tests: differential tests on the pairs (Swift Testing, Linux), sanitization tests on the renderer's entry point (every rejected scheme in `url` and `img`, raw HTML, attribute injection with and without combining marks, 10 000 nested and unclosed tags), writer tests on every rule of the table (crossed tags, whitespace, bullets, trimming, smiley case, markers and placeholders) and on the linear time of eighteen 32 to 172 KB adversarial shapes.
