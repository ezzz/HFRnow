# 0014 — BBCode preview renderer: a local renderer in `HFRParsing`, output through the LOT-034 normalizer

**Status:** Proposed — 2026-11-02 (session `cloud/lot-097`, first deliverable of [LOT-097](../lots/LOT-097-bbcode-preview-renderer.md), [#189](https://github.com/ezzz/HFRnow/issues/189); accepted when merged by the orchestrator or the maintainer)

## Context

FEAT-013 ([#157](https://github.com/ezzz/HFRnow/issues/157), proposed by Bybifok) asks for a preview of a message "exactly as HFR will render it" before it is sent. The legacy app has no preview (the lot's legacy sources are empty; the only BBCode code in the legacy Swift layer is the insertion engine, `HFRswift/Swift/ReplyComposer.swift:99-205` at `2440d79`, which wraps a selection in tags and never renders). The reader shows posted messages through the chain of [ADR 0006](0006-content-normalization-in-parsing.md): HFR's HTML → `MessageContentNormalizer` (LOT-034, the sanitizer of record) → `MessageContent` → the app's `TopicHTMLBuilder` and `ReaderWebController` (LOT-083: `hfrreader:` scheme, CSP `script-src 'none'`, content JavaScript off, images through the cookie-less client and policy C).

What HFR does with BBCode is known only from the captures of run 9 ([#400](https://github.com/ezzz/HFRnow/pull/400), 2026-11-02, [HFR-PROTOCOL §6b "BBCode round trip"](../HFR-PROTOCOL.md#6b-live-observations-from-the-capture-corpus-lot-001-2026-10-26)): `W61` posted one message holding every tag of the composer toolbar help (`R40a`: `b i u strike spoiler quote url img fixed email cpp` and the bullet `[*]`), plus the two forms of `url`, a `color=` and a `list` tag, nested and unclosed tags and raw HTML characters; `R95c` is its edit form (the source comes back byte for byte, CRLF kept) and `R95d` is HFR's own preview, `POST /apercu.php` (form `apercu_form` of every composer: `hash_check`, `apercu_contenu`, `apercu_smiley`, `config`), whose `body.reponse` equals the thread page's message body once whitespace is removed, apart from the opening `<p>` (measured on the raw pages). HFR has at least two renderings of one source: the message and `/apercu.php` agree, the "Vue Rapide" review under the edit form writes `[img]` as a link (`R95c`). `R95h` shows BMP emoji rendered as text.

Questions the issue leaves to this ADR: where the renderer lives (`HFRParsing` or the app), its input and output, how it stays faithful to HFR's rendering when only one pair per tag exists, and its security model.

### Options considered

1. **Local renderer in `HFRParsing`, producing `MessageContent` through the LOT-034 normalizer.** BBCode text → an HTML tree shaped as HFR's rendered message (only the shapes the pairs prove) → `MessageContentNormalizer` → `MessageContent`. The reader displays it with the code it already has.
2. **Local renderer in the app**, writing HTML strings or an `AttributedString` directly. Rejected: ADR 0002 keeps SwiftSoup out of the app, so the app would be a second producer of message HTML outside the sanitizer of record (ADR 0006), with its own escaping and its own stylesheet to keep in step with the reader; and it would not be tested on Linux against the captures.
3. **Server preview**: `POST /apercu.php` through the account's session, a flow in `HFRClient`. The only rendering that is exact by construction, smileys included. Rejected as the lot's deliverable: it needs a logged-in session and a `hash_check`, one request per preview (a preview while typing becomes a stream of POSTs to HFR), does not work offline, and sends the draft to HFR before the member decided to post it. It stays the **oracle** of the local renderer's tests, and a later lot may add it as an "exact preview" action if the local renderer's gaps matter to users; nothing here precludes it.
4. **A typed BBCode AST as a public type in `HFRModels`**, rendered by the app. Rejected for the same reason as ADR 0006 option 3: a second renderer of message content with its own CSS; the AST stays an internal detail of the renderer (option 1) and becomes public only when a second consumer exists (the insertion engine of LOT-085 and the toolbar of LOT-174 work on the text, not on a tree).
5. **Port of a third-party BBCode parser** (ultra-hfr `HFRContent`, MPL-2.0; redface2 `BbcodeContentParser`). Rejected: ideas only, no copy (license and AGENTS.md §3.3); both target their own rendering, not HFR's HTML shapes.

## Decision

Option 1.

### 1. Module and shape

- `BBCodeRenderer` is a public, pure function of `HFRParsing`: `render(_ source: String, options: BBCodeRenderOptions = .init()) throws(ParsingError) -> MessageContent`. No I/O, no global state; only a backend failure throws (`malformedDocument`), as `MessageContentNormalizer.normalize(contentHTML:)`. It depends on LOT-034 (the normalizer) and LOT-020 (`HFRURL`); `scripts/check-lot-deps.py` keeps passing (`HFRParsing` → `HFRParsing`).
- Internally, two stages, both `internal`: a **parser** (source → a flat list of nodes: text, line break, inline tag, block tag, with every unmatched or unknown bracket kept as text) and a **writer** (nodes → a SwiftSoup tree with the HFR shapes, built bottom-up on an explicit stack, as LOT-034 requires). The tree goes to the normalizer's internal `normalize(_ content: Element, relativeTo:)`. The public surface is `render` alone.
- `BBCodeRenderOptions` carries what HFR's own preview form takes: `smileysEnabled` (the composer's `smiley` checkbox, sent as `apercu_smiley`; HFR reads the value: checked disables smileys, HFR-PROTOCOL §6b "Checkbox values") and the **smiley table** the substitution reads (codes → image URLs, built by the app from `CommonSmileyCatalog` and the member's personal smileys). The table is data passed in, never a dependency of `HFRParsing` on the app or on `HFRStorage`.

### 2. Input and output contract

- **Input**: the composer's text as the posting flow will send it. The renderer accepts `\r\n`, `\n` and `\r` as one line break (LOT-048 sends CRLF, `PostingBody`); it renders characters above U+FFFF as text, because LOT-048 refuses such a text before any request (`W12`: HFR would truncate), so the preview never shows a message HFR will cut.
- **Output**: a `MessageContent` **indistinguishable from the one the reader will get once the message is posted**: `html` is the normalized body, `signatureHTML` is nil (the signature is HFR's, added at post time, never previewed), `images`, `smileys`, `links` and `embeds` are the typed lists the normalizer derives, so the reader applies the same image policy, smiley bundling and video placeholders to the preview as to a posted message. The context contract of LOT-034 applies unchanged: `html` is body markup for element content only.
- **Fidelity target**: for every captured pair, `render(source)` equals `normalize(HFR's rendered body)` field by field. The oracle body is the inner HTML of `body.reponse` without the page template's own leading line break and without the `clear: both` trailer (which the normalizer drops anyway), with exactly two reductions, both documented in the spec: the opening `<p>` of the thread shape is added to the `/apercu.php` body (the measured difference between the two), and the `\r` HFR leaves before each `<br />` is removed (whitespace, invisible). Nothing is reduced on the renderer's side.

### 3. Faithful only where proven

- The writer knows **one shape per tag**, copied from a captured pair and cited in the spec's rendering table ([LOT-097 §Behaviour](../lots/LOT-097-bbcode-preview-renderer.md#behaviour)): `b` → `strong`, `i` → `em`, `u` → `span.u`, `strike` → `strike`; `spoiler` and `quote` close the paragraph and open `div.container > table.spoiler|quote > tr.none > td` with their header (`b.s1Topic` "Spoiler :" / `b.s1` "Citation :"), the spoiler body in `div.Topic.masque > p`; `fixed`, `code` and `cpp` close the paragraph and open `table.fixed|code > tr.none > td`, the code body as `ol.olcode > li` per line; `url` (both forms) → `a.cLink`; `img` → `img` with `alt` and `title` equal to the URL. Attributes HFR adds and the normalizer drops (`onclick`, `style="cursor:pointer;"`, `id="codeN"`, `onload`, `style="margin: 5px"`, `target`, the header's `font-family`) are not emitted: they are outside the ADR 0006 contract, and equality is measured after normalization.
- **Everything else is text.** A tag outside the table, a closing tag without its opening, an opening tag never closed, `[color=…]`, `[list]`, a second `[*]` on a bullet line: the brackets stay in the text, which is what HFR does on the three cases captured (`R95d`: `[color=#FF0000]red[/color]`, `[list]`, `[b]unclosed bold`). This is also the acceptance criterion "unknown tags are shown as text, never as HTML".
- **Where one pair allows several rules, the spec picks the narrowest rule that reproduces the pair and names the capture that settles it.** Today: the width of a run of spaces in `fixed` and `code` (two run lengths observed, with different `&nbsp;` phases), the bullet `[*]` (one sample: the first `[*]` opens `ul > li` holding the rest of the line, the next one on that line is text), the line break that follows a block, the trailing `<br />` HFR adds inside a `quote` body and not inside a `spoiler` body.
- **Known not to be rendered identically** until a capture settles it (named here as the issue asks; each is a row of the spec's "Pending capture" list and of the capture issue opened by this lot): smiley codes (standard `:name:` and personal `[:name]`, no pair with `apercu_smiley=0` and a code in the source, so the substitution ships as a table hook that stays empty: codes are shown as text); the toolbar's colour syntax (`TAinsert('['+bgColor+']', …)`, `R40a`: `[#RRGGBB]…[/#RRGGBB]`, never posted; `W61` used `[color=]`, which HFR ignores); `[email]`; bullets on several lines and without `[list]`; `[cpp]` syntax colours (one keyword seen, `int` in `span[style=color:blue]`; the renderer emits a plain `code` block, so a `cpp` block previews without colours); `[quotemsg=…]` (the prefill of a quote, `R41a`: its rendered header `b.s1 > a.Topic` is in the corpus, the pair source → header is not); nested blocks (quote in quote, formatting across lines, BBCode inside `[url=]`); `url` and `img` with another scheme, no scheme or a non-image target, and bare URLs in text (auto-linking is not observed); runs of spaces and tabs in plain text; empty tags; the limit HFR puts on message length and nesting depth.
- A fidelity gap is a **difference to list, never a guess to fill**: the renderer is extended tag by tag as pairs land (each new pair becomes a differential test first), and the preview says nothing about how exact it is; LOT-152 decides whether to label it "aperçu" in the UI.

### 4. Security model

- **No markup from user text, ever.** The writer creates elements and attributes only from its fixed table; the member's text enters the tree as text nodes and attribute values through the DOM API, never through string concatenation, so `<b>`, `&`, `"` and `javascript:` in a message are data (`R95d` shows HFR escaping them too: `&lt;b&gt;`, `&amp;`, `&#034;`).
- **The sanitizer of record runs on the preview as on every message.** The tree goes through `MessageContentNormalizer`: allow-listed elements, attributes and classes, `on*` and `id` dropped, every `href` and `src` resolved and kept only with an `http(s)` scheme (ADR 0006 amendment 1), so `[url=javascript:…]` previews as text and `[img]data:…[/img]` is removed, whatever HFR would do with them (not captured, and irrelevant to our own display).
- **The same display stack, nothing weaker.** LOT-152 shows the preview with the reader's `TopicHTMLBuilder` and `ReaderWebController` (`hfrreader:` scheme, CSP `default-src 'none'; script-src 'none'`, content JavaScript off, `reader.js` in its own content world, every image through the cookie-less client and policy C, link taps handed to the app). A preview never gets a second web view, a `loadHTMLString` with a file base URL (the legacy hazard of audit C §5.2) or a relaxed policy. An `[img]` in a draft is therefore fetched with the same rules as an image in a posted message: blocked on private hosts, third-party hosts on tap or per the setting.
- **Local and silent.** Rendering sends nothing anywhere: no request to HFR, no token, no cookie; the draft leaves the device only when the member sends it. The preview cannot be flood-limited, logged out or rate-limited, and works offline.
- **Bounded work.** The parser is linear in the source length; the writer assembles the tree bottom-up on an explicit stack (SwiftSoup's recursive `appendChild`, LOT-034 learning), so nesting depth is bounded by memory, not by the stack; the LOT-034 check at 10 000 nested tags on a 512 KB-stack thread is repeated for the renderer. HFR's own limits are not known and not imitated (pending capture).

### 5. Where the facts live

The rendering table (tag → shape → capture) is in the lot spec; verified facts go to HFR-PROTOCOL §6c under `### LOT-097` once a parser test asserts them (§6b already holds the round-trip facts of run 9). The module rules (ADR 0001, 0002, 0006, 0008) are unchanged: the renderer is one more pure function of `HFRParsing`, and `HFRClient` is not involved.

## Consequences

- The preview and the posted message are rendered by **one** code path after the BBCode stage: the reader's stylesheet, image policy, spoiler toggle and smiley bundling apply to both without duplication, and a LOT-034 fix reaches the preview for free.
- Fidelity is **measured** (differential tests on every captured pair, `W61`/`R95c`/`R95d` first, `R95h` for emoji), **bounded** (the spec's rendering table and pending list say exactly what is and is not reproduced) and **extensible** (a new pair → a new test → a new row). The first capture batch leaves visible gaps (smileys above all): the renderer ships with them named, and the capture issue opened by this lot (`host: mac`) lists what the next Mac session captures, through `/apercu.php` (no write needed: `R95d` proves it renders without posting).
- `/apercu.php` is documented as HFR's own preview and stays available for a later "exact preview" flow in `HFRClient`; choosing it as a default would reverse the "local and silent" property and is a decision for the operator, not for a lot.
- The app side (LOT-152) is thin: call `render`, build a `ReaderPage` with one message, show it in the reader stack. It also owns the smiley table (catalogue plus personal smileys) and the `smileysEnabled` flag taken from the composer's checkbox.
- Tests: differential tests on the pairs (Swift Testing, Linux), sanitization tests on the renderer's entry point (every rejected scheme in `url` and `img`, raw HTML, `on*`-looking text, 10 000 nested tags), parser tests on the text-fallback rules (unknown, unclosed, stray closing tags).
