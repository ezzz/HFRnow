## Behaviour

### API

| Type | Members | Rules |
|---|---|---|
| `BBCodeRenderer` (public) | `render(_ source: String, options: BBCodeRenderOptions = .init(), relativeTo page: URL = HFRURL.base) throws(ParsingError) -> MessageContent` | `source` is the composer text; line breaks are read as CRLF whatever it holds (`PostingBody` sends CRLF); the three noncharacter markers (U+FFFF, U+FFFE, U+FDD0) dropped; `page` is the topic the message goes to (relative links resolve as on the posted message). Pure; only a backend failure throws (`malformedDocument`). `signatureHTML` is always nil |
| `BBCodeRenderOptions` (public) | `smileysEnabled: Bool = true`, `smileys: [String: URL] = [:]` | `smileysEnabled` is the composer's `smiley` checkbox read as HFR does (checked = disabled, §6b "Checkbox values"), sent to HFR's own preview as `apercu_smiley`. `smileys` maps a code (`:jap:`, `:D`, `[:user]`, `[:user:1]`) to its image URL; the app builds it from `CommonSmileyCatalog` and the member's personal smileys. ASCII letters matched whatever their case, the longest code at a position (`R32a` `para26366036` renders `:pt1cable:` whole while `:p` is a code), anywhere, inside a URL too (`R443a`: `[url]https://example.invalid/:)[/url]` and the `:/x` of `https://example.invalid/:/x` are substituted), except the `:/` of `://`, which keeps a URL's scheme whole (HFR does not substitute it: `https://` stays); never inside an entity of the escaping (matched on the text as typed) nor inside a held fragment (an `[img]` URL, a raw block); prepared once per table (a trie; equality and hashing of the options read the table, not the trie), a code holding a marker or longer than 64 scalars left out (HFR's limit on a smiley name: pending 11): `alt` is the text as typed, `title` the table's code (`R42` → `R20`: `alt=":d" title=":D"`, the member typed `:d`; two codes equal once folded: the one typed exactly, else the first in code-point order of the code: default, pending 1) |
| `HFRBBCodeWriter` (internal) | `html(for source: String) -> String` | HFR's HTML string for the source, by the passes below, each one scan of the text, all on Unicode scalars (a combining mark after a `"` or a `]` hides nothing) |
| `BBCodeRenderer.contentHTML(for:)` (internal) | `(String) throws(ParsingError) -> String` | the string parsed on the reader's path: a first parse inside the same markup as the thread page, `<table><tr><td><div id="para0">…<div style="clear: both;"> </div></div></td></tr></table>`, serialized back as `MessageBlockParser.contentHTML`; then `MessageContentNormalizer.normalize(contentHTML:relativeTo:)` parses that serialization again. The two parses give the reader's repair of crossed tags (`R20` `para2666649`: 37 `<strong>` for 36 `</strong>` once serialized from the page, 38 for 38 once normalized, asserted; a single parse, or a string ending with an explicit `</p>`, gives 37 for 37) |

### Passes of the writer (HFR's own model, ADR 0014 §1)

1. Line breaks normalized to CRLF; U+FFFF, U+FFFE and U+FDD0 (the markers, three noncharacters) dropped.
2. Raw blocks, `cpp` then `code` then `fixed` (HFR numbers the `cpp` block `code1` before the `code` block `code2`, `R95d`, `R443n`): each `[tag]…[/tag]` pair, non-greedy, its content escaped and taken as typed (brackets inside are text), held in a placeholder. `code` and `cpp` lines are coloured (`R443e`), and in `code` a `[b]…[/b]` within a line is rendered (`R443j`). A raw block inside a raw block (`R443n`; one line only): a `[code]` in a `[cpp]` is a code table inside the cpp item, its content (the line's own HTML) escaped and coloured again; a `[fixed]` in a `[cpp]` or a `[code]` is a fixed table inside the item; a `[fixed]` around a held block loses its tags and keeps its content as text; `[cpp]` in `[code]` and `[code]` in `[fixed]` keep the old default (tags text, pending 11); a tag inside itself closes at the first `[/tag]` (`[code]a [code]b[/code] c[/code]` → `a [code]b` then ` c[/code]`, `R443n`).
3. Whitespace (rule below): a no-break space and a LF become markers, written `&nbsp;` and `<br />` at the end. A LF that a `[*]` line will consume does not start a line (`R443d`).
4. `[img]U[/img]`: `U` without bracket or line break, not empty, escaped into the attribute; held in a placeholder (smileys never touch it, `R443a`).
5. Smileys when enabled, on the text as typed, the whole table in one scan through a trie: at each position the longest code, ASCII letters in any case, not the `:/` of `://`, not inside a held fragment; held in placeholders.
6. `[url=U]text[/url]` and `[url]U[/url]`: `U` without bracket, line break or held fragment (a smiley in `U` makes it text, `R443a`), not empty, escaped into the attribute; then the bare `http://` and `https://` URLs of the text become links (`R443a`, `R443f`), up to the first space, line break, smiley, `<`, `>`, `"`, `[` or `]`, never right after `[url]` nor `=`, never inside a `[url=…]` text.
7. The remaining text escaped once, as HFR does (`&amp;`, `&lt;`, `&gt;`, `&#034;`; `R95d`), a `)` after a typed `"` or `&` getting a space before it (`R443a`, `R443b`: `&#034;oui&#034; )`, `&amp; )`; smileys on or off).
8. `[quote]`, then `[spoiler]`: a `[/tag]` closes the innermost open `[tag]` (nested quotes written inside out); an open or close without its match stays text. **Two levels of quotes at most**: from the third open, an open stays text and the closes pair with the opens that rendered (`R443l`: 30 nested → 2 rendered, 28 opens and 28 closes text); the spoiler has no captured limit (pending 11).
9. `[#RRGGBB]…[/#RRGGBB]` (or `[#RGB]`): the open pairs with the first colour close after it, whatever that close names (`R443n`: `[#0055AA]x[/#0055aa]` renders with the open's case; `[#ff0000]a [#00ff00]b[/#00ff00] c[/#ff0000]` closes at the inner close, the inner open and the outer close stay text).
10. `b`, `i`, `u`, `strike`: each in one non-greedy pass, left to right (a pair closes at the first `[/tag]` after its `[tag]`), so crossed tags come out crossed as HFR writes them and `[b][b]x[/b][/b]` gives `<strong>[b]x</strong>[/b]` (`R443j`). For `b`: `[b][/b]` is text (`R443j`), and a pair whose content holds a block (a quote written by pass 8) loses its tags, content kept (`R443i`); `i`, `u` and `strike` are not captured (pending 11).
11. `[*]`: the first of a line opens `</p><ul><li>` for the rest of the line, the line's break consumed; a next line starting with `[*]` is another item of the same list, the first line without one ends it (`R443d`).
12. `<p>` + text, the paragraph left open as HFR leaves it (the clear trailer closes it, `R20`); placeholders restored, then the markers written (`&nbsp;`, `<br />`), since a held URL may hold one (`[url]a  b[/url]` → `a &nbsp;b`).

### Rendering table (one shape per tag; `R95d` unless noted)

The message is a sequence of paragraphs and blocks. Text and inline tags live in a `<p>`; a block tag closes the paragraph, writes its block, and opens a new paragraph (`</p>…<p>`). The thread page wraps the message in an opening `<p>` that `/apercu.php` omits (`R20` `para2666649` against the `R41a` review; the raw pages of #400); neither closes it (the clear trailer does). HFR writes no `tbody`: the HTML5 tree builder adds one to every table and repairs crossed tags, on both sides, through the reader's two parses (`BBCodeRenderer.contentHTML`, then the normalizer).

### Whitespace rule (one rule; `R20` `para2666649` against the `R41a` prefill, `R27b`, `R95d`)

In a run of spaces and CRs: the first character becomes `&nbsp;` when the run starts a line (right after a LF; **the start of the message is not a line start**: three leading spaces give ` &nbsp; `, `R443g`, while the same three after a line break give `&nbsp; &nbsp;`, `R443n`; in `code`, every run of two or more, and **not** a run of one at a line start, which stays a plain space, `R443g`); a LF that a `[*]` line consumes does not start a line, so the CR of the blank line after a list stays plain (`R443d`: `three\r</li></ul><p>\r<br />[list]`; only the CR case is captured, pending 11); then the run is read two by two, the first of a pair kept (a space as itself, a CR as the `\r` HFR leaves in the text), the second `&nbsp;`; a last one alone kept. A LF becomes `<br />`. The `&nbsp;` is written as the entity, as in HFR's bytes.

## Edge cases

- **Crossed tags** come out crossed and are repaired by the tree builder as on the thread page; the repair reopens the outer formatting element around what follows (`R20`: `<strong>` reconstructed around the next lines after `[u][b]x[/u][/b]`), which the renderer reproduces because it writes the same string, `\r` included.
- **Line break after a block**: `<p>\r<br />…` at the start of the next paragraph; before a block, `…\r<br /></p><div`. Two blocks separated by one line break give a paragraph holding `\r<br />`, kept by the normalizer; two adjacent blocks give an empty `<p>`, dropped on both sides.
- **Bullet line**: the line's `<br />` is consumed by the `</li></ul>`; the `\r` stays inside the `li` (`R95d`, `R95c`).
- **URL schemes**: the renderer never decides; `normalizedURL` does (http(s), absolute against `page`, `hardware.fr` upgraded to https, `hfr-rehost.net` → `reho.st`); `http://` is added first to a URL with no `scheme:` prefix or starting with `www.`, as HFR does (`G3Ferrari`, `www.example.invalid:8080/x`, `R443n`). HFR itself puts `http://` before `javascript:`, `tel:` and `mailto:`, keeps `ftp://`, writes `//host` as `http:////host`, and accepts `ftp://` and a page URL in `[img]` while `[img]javascript:…` and `[img]//host` stay text (`R443f`); the sanitizer keeps its own rule for all of them (intentional difference 2): a URL with a scheme other than http(s) is text or removed, so `[url]tel:0123[/url]` and `[img]ftp://…[/img]` differ from HFR on purpose. A typed `"` in a URL is written `&amp;#034;` in the attribute and `&#034;` in the text, a `&` once in both, and the renderer does the same (`R443f`).
- **Message cut by HFR**: a character above U+FFFF is rendered as text; LOT-048 refuses the send, so no preview of a text HFR would truncate (`W12`) is ever sent.
- **Depth and size**: every pass is one scan (the next closing tag or bracket is searched once and remembered; a rejected URL argument is checked on its slice before any copy; nested blocks are matched in one pass and written in a second; colour closes indexed once with one head index, bare URLs and bullet items each in one scan; the next placeholder remembered for raw blocks; the whole smiley table matched in one scan through a trie prepared once per table, a code longer than 64 scalars left out so a position's walk is bounded whatever the table, a smiley matched in place); each of nineteen 32 to 172 KB adversarial shapes costs about four times more at four times the size (measured; the test asserts under six times plus half a second, where a quadratic pass gives sixteen), with the bundled catalogue plus a thousand personal codes; the whole render grows superlinearly on repeated crossed tags (the normalizer's parse reopens the `<strong>` around what follows: 4.2 s at 64 KB, 14 s at 128 KB, debug build) and quadratically on nested blocks (`[spoiler]`×n; `[quote]` renders two levels since #742, so its depth is no longer an input: both SwiftSoup parses, measured before #742 at 3.6 s + 3.8 s for 1 000 nested quotes, 14 s + 14 s for 2 000; the 12 s of the 10 000-tag check are mostly its 1 000 nested quotes); the reader pays the same on the posted message (ADR 0014 §4, issue #445); LOT-152 renders off the main actor and debounced, and skips the live preview above a depth or size it sets, a SwiftSoup parse being uncancellable (an on-demand preview stays possible).
- **Smiley matching**: on the text as typed, so `")` never gives a `;)` smiley through `&#034;)`: HFR writes a space before a `)` that follows a typed `"` or `&` (`&#034;oui&#034; )`, `&amp; )`, `R443a`, also with smileys off, `R443b`) and the renderer does the same, in text and in `code` lines (not in `fixed`: pending 11); never inside a held fragment (an image, a raw block: `[img]https://example.invalid/:o.png[/img]` stays whole, `R443a`); anywhere else, **URLs included** (`[url]https://example.invalid/:)[/url]` gives the smiley and leaves the tag as text; in a bare URL the link stops before the `:/` of `https://example.invalid/:/x`, which is the smiley, `R443a`), except the `:/` of `://`; ASCII letters matched whatever their case, the longest code first (`R32a`: `:pt1cable:` whole; `R443n`: `:p:pfff:` gives the smiley `:p:` then `pfff:`, `:D:dtc:` the smiley `:D:` then `dtc:`, because HFR knows `:p:` and `:D:` as codes), two codes equal once folded going to the one typed exactly, else the first in code-point order, glued words included (`oui:p`, `bonjour:)` give a smiley, `R443a`): `:p:` and `:D:` are not in the bundled catalogue (follow-up [#796](https://github.com/ezzz/HFRnow/issues/796)), the renderer takes the table it is given.
- **Markers and placeholders**: a `[url]`, `[url=]` or `[img]` whose URL holds a placeholder (a raw block inside it) is text; a typed `\u{FFFF}<digits>\u{FFFF}` loses its markers before any pass, so no text can name a held fragment; a `[*]` consumes its own line break only (held as a marker), never a `<br />` the writer wrote in a block header.
- **Defaults for uncaptured cases** (each named in Pending capture 11): `[url=…]` around `[b]` formats the text (and `[b][url]…[/url][/b]`: both captured, `R443h`); the start of a `[b][/b][b]x[/b]` sequence, `[i]`/`[u]`/`[strike]` empty or around a block, `[b]` in `[cpp]` or `[fixed]`, `[cpp]` in `[code]` and `[code]` in `[fixed]`; a `[*]` inside `[b]…[/b]` opens a bullet in the middle of the pair (crossed, repaired).

## Intentional differences from HFR

1. **Attributes outside the ADR 0006 contract are not written** (`onclick`, `style="cursor:pointer;"`, `onload`, `style="margin: 5px"`, `target="_blank"`, `rel="nofollow"`, `id="codeN"`, the header's `font-family`): the normalizer drops them from posted messages, so the preview equals the posted message, not HFR's bytes.
2. **Non-http(s) URLs** are text (links) or removed (images), whatever HFR renders: the preview is sanitized by the same rules as every message.
3. **`[email]` is not a link, nor a `mailto:` anywhere**: `[email]a@b.c[/email]` stays text (HFR links it with `mailto:`, `R443c`); an address in plain text is not linked by HFR either. Reason: the sanitizer would unwrap the `mailto:` link to its text anyway, so the visible difference is only the tags; it is a gap rather than a decision (#796).

## Learnings

To copy into AGENTS.md §11 when the lot closes:

- HFR renders BBCode by rewriting the text tag by tag, not by matching a tree: crossed tags come out crossed (`<span class="u"><strong>x</span></strong>`) and the browser repairs them. A renderer that wants the same display writes the same string and lets the same tree builder repair it; a DOM-building renderer diverges on every crossed case.
- The quote prefill (`[quotemsg=…]`) is a source → rendering pair for every message of the corpus whose quote form was captured, so BBCode facts can be read from `R41a`/`R41b`/`R42` against `R20` without a new capture; it rewrites `[img]` as `[url]` and drops the citation the message starts with.
- HFR has several renderings of one source: the message (= `/apercu.php` modulo whitespace and the opening `<p>`) and the "Vue Rapide" reviews (`[img]` as a link, no smiley). A rendering fact names which one it comes from.
- The composer's colour button inserts `[<colour>]…[/<colour>]`, not `[color=…]`: read the toolbar's `TAinsert` calls before writing a capture checklist of tags.
- Swift reads `\r\n` as one `Character`: a `replacing("\n", …)` on a `String` never matches inside a CRLF; work on `unicodeScalars` when CR and LF must be told apart.
- The reader parses a message twice (the page, then the normalizer's body fragment), and the first serialization of a crossed `<span><strong>x</span></strong>` loses a `</strong>` that the second parse reopens; a single parse, or a string ending with an explicit `</p>` where HFR leaves the paragraph open, gives another tree. A renderer that must match the reader parses its string the same number of times and writes HFR's bytes, open paragraph included.
- HFR's preview is a chain of replacement passes over one string, each pass reading the previous pass's output: that explains `[b]` rendered inside `[code]` (the inline pass runs after the raw one), a `[code]` in a `[cpp]` whose content is escaped and coloured again, a `[url]` made text by a smiley substituted first, and a `[b]` around a quote losing its tags. Read an unexpected capture as "which pass ran before which", not as a special case.
- A capture can contradict its own issue: #742 fact 7 said the message start is a line start, `R443g` bytes (` &nbsp; `, not `&nbsp; &nbsp;`) say it is not. Compare the bytes of the capture, not the summary.
- `request_body` of a capture can be damaged by the anonymizer (`R443c`, `R443f`: `%redacted`); a differential test decodes line by line and says which line it skips.
